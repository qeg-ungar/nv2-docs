Software Organization¶

This page describes the software that controls the NV2 setup: the two Python packages that run the instruments (Qudi and QUA), how they are organized in a single workspace, how to set that workspace up on a new computer, and how the code is kept under version control.

Overview¶

The setup is controlled by two open-source Python packages, which divide the hardware in the system block diagram between them:

  • Qudi[1] runs the “slow” instruments and the imaging. It handles confocal scanning of the piezo stage with photon counting on the NI DAQ card, acquisition on the two widefield cameras (the SPC3 SPAD camera and the Hermes camera), wide-range CW ODMR scans, monitoring of the photodetector and SPCM signals, and control of the alignment laser and the digital switches.

  • QUA[2], the pulse-level language of Quantum Machines, programs the QM OPX+ for pulsed experiments. The OPX+ acts as the arbitrary waveform generator (IQ waveforms for the MW chains, RF pulses, and TTL gating of the lasers) and counts photons by time-tagging the SPCM pulses on its analog input, all synchronized within one pulse sequence. The QUA scripts also set the SRS SG384 local oscillators before each run.

Qudi can also run long experiments automatically. A script executed through Qudi’s Jupyter kernel periodically re-tracks the NV emitter (the scanning optimizer re-centers the piezo on the fluorescence spot) and then sends a trigger to the OPX+ through an NI digital line (the AWG trigger switch), so the OPX+ resumes the pulse sequence and data collection with the NV back in focus. This lets an experiment average for hours while staying on the same emitter (see Automation).

Environment and workflow¶

All of the control code lives in one workspace folder, opened as a single VS Code workspace and run from a single Python virtual environment:

  • qudi-iqo-modules/: our fork of the Qudi measurement modules, installed in editable mode so lab changes (e.g. the DLnsec laser driver) take effect without reinstalling.

  • qua-libs/: our fork of the Quantum Machines example library; the NV2 scripts are in Quantum-Control-Applications/Optically addressable spin qubits/NV2/.

  • qudi-configs/: the Qudi configuration files for NV2.

  • python notebooks/: Jupyter notebooks that script Qudi through its kernel.

A typical session starts Qudi with the NV2 configuration, uses the confocal scanner to find the NV or array of interest and optimize its position, and then runs QUA scripts from VS Code for calibrations and pulsed experiments. Qudi saves its data to the data directory set in its configuration, with daily subfolders, and the QUA scripts save to a Data folder next to the NV2 script folder.

Qudi¶

Qudi is a modular Python suite for experiment control and data processing, developed at the Institute for Quantum Optics in Ulm[1]. It is split into two packages:

  • qudi-core is the framework: the module manager, the configuration system, the GUI manager, data storage, and the IPython kernel used by notebooks (documentation).

  • qudi-iqo-modules provides the measurement modules: confocal scanning, time series, CW ODMR, camera, laser, switches, and others. Its docs/ folder has setup guides for the main toolchains.

Hardware, logic, and GUI modules¶

Every Qudi measurement module is one of three types, arranged in a one-way hierarchy[3]:

  • Hardware modules wrap a single instrument behind an abstract interface (e.g. a microwave source, a finite-sampling input, a camera). They do not control other modules. Because logic only talks to the interface, a real instrument can be swapped for another model or a dummy without changing the logic.

  • Logic modules are the core of a measurement: they run it, process and save the data, and coordinate one or more hardware (or other logic) modules. Each runs in its own thread, and its methods form the API that notebooks and scripts call.

  • GUI modules are Qt windows built on top of logic modules. They contain no measurement logic of their own.

Modules declare their dependencies with connectors, their static settings with config options, and any state to remember between sessions with status variables. The module manager loads and activates modules (and everything they depend on) on request.

Configuration file¶

A Qudi session is built from a configuration file: a YAML text file with a .cfg extension, read once at startup[4]. It has a global section (data directory, startup modules, server ports, GUI stylesheet) followed by gui, logic, and hardware sections. Each module entry gives a unique name, the module class (module.Class), its options, and a connect block that wires its connectors to other modules by name. For example, the confocal scanning toolchain in the NV2 configuration (trimmed):

gui:
    scanner_gui:
        module.Class: 'scanning.scannergui.ScannerGui'
        connect:
            scanning_logic: scanning_probe_logic
            data_logic: scanning_data_logic
            optimize_logic: scanning_optimize_logic

logic:
    scanning_probe_logic:
        module.Class: 'scanning_probe_logic.ScanningProbeLogic'
        connect:
            scanner: ni_scanner

hardware:
    ni_scanner:
        module.Class: 'interfuse.ni_scanning_probe_interfuse.NiScanningProbeInterfuse'
        connect:
            scan_hardware: 'ni_finite_sampling_io'
            analog_output: 'ni_ao'
        options:
            ni_channel_mapping:
                x: 'ao0'
                y: 'ao1'
                z: 'ao2'
                APD1: 'PFI15'

Opening scanner_gui in the Qudi manager loads the whole chain down to the NI card. The NV2 configuration (qudi-configs/SPUD202609.cfg) defines these toolchains:

Notebooks and scripting¶

Qudi serves its active modules to a Jupyter kernel, so experiments can be scripted in a notebook using the same logic modules the GUIs use[5]. The qudi kernel does not start Qudi itself; it connects to a running Qudi instance through the local namespace server (namespace_server_port in the configuration, 18861 by default) and exposes each active module by its configured name. For example, with the dlnsec_laser module active:

laser_control = dlnsec_laser
laser_control.set_power(10)  # mW
laser_control.on()

To run a notebook, start Qudi and load the NV2 configuration, activate the modules the notebook uses in the Qudi manager, then open the notebook in VS Code and select the qudi kernel. The workspace’s QUDI_MIGRATION.md covers re-registering the kernel and fixing a stale kernel path in VS Code.

QUA¶

QUA is a Python-embedded language for pulse-level control[2]. A QUA program describes which pulses to play on which outputs, which signals to measure, the real-time variables and loops that sweep parameters, and how results are processed. It is sent to the OPX+, which compiles it and executes it in real time on its pulse processor, with deterministic timing in 4 ns clock cycles. Each NV2 script follows the same pattern: import the configuration, write the program inside a with program() block, connect to the OPX+ with a QuantumMachinesManager, and either simulate the program or open a quantum machine with the configuration and execute it, fetching and plotting the results live.

Configuration¶

The configuration is a Python dictionary (config in NV2/configuration.py) that maps the physical OPX+ ports to the logical objects the program uses[6]:

  • Controllers list the OPX+ ports in use, with their DC offsets and delays.

  • Elements are the components the program addresses. Each is assigned the OPX+ outputs that drive it (a single analog output, an I/Q pair of analog outputs, or a digital output), and a readout element is also assigned the OPX+ analog input it is read on. Each element also has an intermediate frequency (IF) and a set of named operations. The configuration keys are named from the element’s point of view, so singleInput, mixInputs, and digitalInputs refer to OPX+ outputs, and an element’s outputs refers to an OPX+ input.

  • Operations point to pulses, which have a length and waveforms: one for an element on a single analog output, I and Q for an element on an I/Q pair. Measurement pulses also define how the signal on the OPX+ input is acquired. The mixer entry holds the IQ correction matrix from the IQ calibration.

MW_switch replaced the former AOM1 laser element on digital output 1. AOM1 and its readout partner SPCM1 are still defined in configuration.py, but AOM1 now drives the MW switch output, so NV2 sequences use AOM2 and SPCM2.

configuration.py also connects to the SG384 through SG384.py (a small PyVISA driver) and sets its frequency, amplitude, and IQ modulation when the configuration is imported. Running any NV2 script therefore reconfigures the SG384 to the values in configuration.py.

Writing programs¶

The main QUA statements used in the NV2 scripts are:

  • play(operation, element) plays a pulse on an element, modulated at the element’s IF; amp(...) scales its amplitude and duration= sets its length in real time (in 4 ns clock cycles).

  • measure(operation, element, ...) plays a readout and acquires the returning signal; for the SPCM, time_tagging.analog(...) records the arrival time of each photon pulse and returns the count.

  • align() makes elements wait for each other before continuing (with no arguments, all elements), and wait() inserts a delay, so the MW, laser, and readout happen in the right order.

  • declare() creates real-time variables, and for_ loops sweep them on the OPX+ (with from_array from qualang-tools to loop over a NumPy array).

  • save() sends values to streams, and the stream_processing() block buffers and averages them on the OPX+ before they are fetched.

For example, the core of the time-Rabi script, shown here with the NV2 elements, sweeps the MW pulse duration t and reads out the fluorescence after each pulse:

with for_(n, 0, n < n_avg, n + 1):
    with for_(*from_array(t, t_vec)):
        play("x180" * amp(1), "NV", duration=t)  # MW pulse of variable length
        align()                                  # laser readout after the MW pulse
        play("laser_ON", "AOM2")
        measure("readout", "SPCM2", time_tagging.analog(times, meas_len_2, counts))
        save(counts, counts_st)
        wait(wait_between_runs * u.ns)

The unmodified default scripts address AOM1 and SPCM1. On NV2, switch them to AOM2 and SPCM2, as in the modified 05a_cw_odmr.py.

Setting Up the Workspace¶

A clean copy of the NV2 workspace is maintained as a reference repository, qeg-ungar/nv2-workspace. It holds the two forks as git submodules, plus the files needed to get started: the Qudi configurations, the QUA configuration, and the SG384 driver. It is a copy of the workspace on the lab computer, updated whenever that workspace is in a known-good state. The layout is:

nv2-workspace/
├── .venv/                        Python virtual environment (not tracked)
├── qudi-iqo-modules/             submodule: fork of Ulm-IQO/qudi-iqo-modules (editable install)
├── qua-libs/                     submodule: fork of qua-platform/qua-libs
│   └── Quantum-Control-Applications/Optically addressable spin qubits/NV2/
├── qudi-configs/                 default.cfg and the NV2 configuration
├── python notebooks/             notebooks run on the qudi kernel
├── QUDI_MIGRATION.md             environment notes and troubleshooting
└── workspace_sam.code-workspace  VS Code workspace

The commands below are for the Windows lab computer, run from the workspace folder in a VS Code terminal.

  1. Get the code. Clone the workspace with both submodules (see Version Control):

    git clone --recurse-submodules https://github.com/qeg-ungar/nv2-workspace.git

    To build it from scratch instead, fork qudi-iqo-modules and qua-libs on GitHub and clone both forks into one folder.

  2. Create the Python environment. Create a virtual environment with Python 3.11 in the workspace folder, select it as the interpreter in VS Code (Python: Select Interpreter), and save the workspace (File → Save Workspace As):

    py -3.11 -m venv .venv

  3. Install the QUA packages. Install the qua-libs requirements (including qm-qua, qualang-tools, and PyVISA):

    .venv\Scripts\python.exe -m pip install -r qua-libs\requirements.txt

    The NV2 folder must contain configuration.py and SG384.py. They are already in the reference workspace; in a fresh fork, copy them into the NV directory. The OPX+ and SG384 network addresses are set in configuration.py.

  4. Install Qudi. Install qudi-core from PyPI (not from source), then install qudi-iqo-modules from the cloned fork in editable mode, following the qudi-iqo-modules installation guide:

    .venv\Scripts\python.exe -m pip install qudi-core

    .venv\Scripts\python.exe -m pip install -e qudi-iqo-modules

    Then apply the two package fixes in QUDI_MIGRATION.md: pin PySide6 to 6.11.0 (6.12 blanks the scanner GUI’s input boxes), and make sure pyserial, not the unrelated serial package, is installed.

  5. Set up the configuration. Create qudi-configs/ (already present in the reference workspace) and copy in default.cfg from qudi-iqo-modules/src/qudi/default.cfg and the NV2 configuration (SPUD*.cfg). In the NV2 configuration, set default_data_dir to the data folder on this computer.

  6. Register the notebook kernel:

    .venv\Scripts\qudi-install-kernel.exe

  7. Start Qudi. Run qudi from the workspace folder, then load the NV2 configuration in the Qudi manager (File → Load configuration → qudi-configs/SPUD*.cfg). Alternatively, pass it at startup:

    .venv\Scripts\qudi.exe -c qudi-configs\SPUD202609.cfg

Version Control¶

The workspace is a git repository in its own right (the parent), with the two forks inside it as git submodules:

Folder

Repository

Contents

parent

qeg-ungar/nv2-workspace

Lab files: qudi-configs/, notebooks, notes, the VS Code workspace

qudi-iqo-modules/

qeg-ungar/qudi-iqo-modules, branch nv2-qeg (fork of Ulm-IQO/qudi-iqo-modules)

qua-libs/

qeg-ungar/qua-libs, branch nv2-qeg (fork of qua-platform/qua-libs)

In the reference workspace, the lab code in each fork is on the nv2-qeg branch; the branch is also recorded in the parent’s .gitmodules. The forks’ main branches hold an earlier version of the lab code and are not used.

The parent stores the lab’s own files and, for each fork, a pointer to one specific commit; it does not store the fork files. Each fork keeps its own history, so it can still pull updates from its upstream project. Every parent commit therefore records a combination of lab files and fork versions that work together, and you can return to it if a later update breaks something. The rule to remember is commit in the fork first, then in the parent.

All repositories are public, so never commit passwords, tokens, or measurement data. The workspace’s .gitignore excludes the virtual environment, data folders, and logs.

First-time setup on a new computer¶

After cloning with --recurse-submodules, make git push also push any unpushed fork commits, and put both forks on their nv2-qeg branch (a fresh clone leaves them at a fixed commit, and commits made there would not belong to any branch):

git config push.recurseSubmodules on-demand

git submodule foreach git switch nv2-qeg

Before you start working¶

git pull

git submodule foreach git pull

Saving and sharing changes¶

  • Parent files only (notebooks, configurations): commit and push as in any repository.

  • Files inside a fork (e.g. a QUA script in qua-libs):

    1. Commit in the fork:

      git -C qua-libs add -A

      git -C qua-libs commit -m "Describe the change"

    2. Record the fork’s new commit in the parent:

      git add qua-libs

      git commit -m "Update qua-libs: short summary"

    3. Push. This pushes the fork first, then the parent:

      git push

  • Both: commit in each fork you changed, then make one parent commit with the parent files and the updated fork pointers, and push.

To bring in upstream updates to a fork, click Sync fork on its GitHub page, pull it locally (git -C qudi-iqo-modules pull), check that Qudi and the QUA scripts still run, then commit the updated pointer in the parent.
